# 替换实际运行截图指南

> 用途：把报告里的 `【截图：...】` 占位符和部分原型图，替换成在服务器上实际运行、实际测试得到的截图。
> 适用：队友提供了一台 Linux 服务器，让你远程访问并运行 DecisionJury。

---

## 0. 先向队友确认这些信息

不要一上来就 SSH，先把下面几项问清楚，能少走很多弯路。

| 需要确认 | 示例 | 为什么重要 |
|---|---|---|
| 服务器地址 | `10.0.x.x` 或域名 | SSH 连接目标 |
| SSH 端口 | 默认 22，也可能是 2222 | 连接命令要带 `-p` |
| 登录方式 | 密码 / `.pem` 密钥 / 已配置免密 | 决定怎么登录 |
| 项目路径 | `/home/xxx/DecisionJury` | 后面所有命令都在这个目录 |
| 部署方式 | `screen` 脚本 或 `Docker Compose` | 启动、重启、看日志命令不同 |
| 访问地址/端口 | `:5173`（screen）或 `:8088`（Docker） | 浏览器截图地址不同 |
| 代码版本 | 分支 + commit，例如 `dev@5abbc86` | 报告要写清楚截图对应版本 |
| 是否配了 Key | `DEEPSEEK_API_KEY` 是否已配置 | 决定截图是真实模型还是 mock 兜底 |
| 是否允许跑测试 | 是否允许占用 CPU、是否可用内存库 | 测试过程截图需要跑 pytest |
| 是否有 sudo | 是否需要装依赖/开端口 | 部分操作需要 |
| 端口是否放行 | 服务器安全组/防火墙是否开放 5173/8088 | 决定要不要用 SSH 隧道 |

> 关键：如果服务器上已经有队友在跑服务，先问清楚**能不能重启**、**数据库是不是演示库**，不要直接 `down -v` 或重新建库。

## 1. 本地连接服务器

### 1.1 基础 SSH

```bash
# 密码登录
ssh <user>@<server-ip>

# 非默认端口
ssh -p 2222 <user>@<server-ip>

# 密钥登录（Windows PowerShell / Git Bash 均可）
ssh -i C:\path\to\key.pem <user>@<server-ip>
```

登录后先确认项目目录：

```bash
cd ~/DecisionJury        # 按队友给的实际路径
pwd
git rev-parse HEAD       # 记录 commit，后面报告要写
git branch --show-current
```

### 1.2 如果端口没有对公网开放：用 SSH 隧道

屏幕方案（前后端/RAG 都只监听 127.0.0.1 或只开放前端 5173）：

```bash
ssh -L 5173:127.0.0.1:5173 \
    -L 8000:127.0.0.1:8000 \
    -L 8001:127.0.0.1:8001 \
    <user>@<server-ip>
```

Docker 方案（前端映射到宿主机 8088）：

```bash
ssh -L 8088:127.0.0.1:8088 <user>@<server-ip>
```

保持这个 SSH 窗口不要关，然后在本地浏览器访问：

- screen 方案：`http://127.0.0.1:5173/`
- Docker 方案：`http://127.0.0.1:8088/`
- 后端 Swagger：`http://127.0.0.1:8000/docs`
- RAG Swagger：`http://127.0.0.1:8001/docs`

## 3. 启动服务

### 3.1 方案 A：screen 脚本（Linux 裸机）

首次安装：

```bash
cd ~/DecisionJury
bash deploy/install.sh
nano .env          # 至少确认 ENV=production、DEEPSEEK_API_KEY（如果需要真实模型）
```

启动/停止/看日志：

```bash
bash deploy/start.sh
screen -ls
tail -n 50 logs/backend.log
tail -n 50 logs/rag.log
tail -n 50 logs/frontend.log

# 停止
bash deploy/stop.sh
```

启动后访问：

```bash
curl http://127.0.0.1:8000/api/health
# 期望：{"success":true,"data":{"status":"ok","version":"1.0.0"},"message":""}
```

### 3.2 方案 B：Docker Compose

```bash
cd ~/DecisionJury
cp deploy/.env.docker.example .env    # 仅当 .env 不存在
vim .env                              # 填 DEEPSEEK_API_KEY（如需真实模型）

docker compose up -d --build
docker compose ps                     # 等三个服务 healthy
docker compose logs -f backend        # 看后端日志
```

访问：

```bash
curl http://127.0.0.1:8088/api/health
```

停止/重启：

```bash
docker compose stop
docker compose start
docker compose restart backend
docker compose down        # 保留数据库 volume
# 不要随便 down -v，会清空数据库
```

> 截图建议：`docker compose ps` 显示三个服务 `healthy` 的终端窗口，是一张很好的“项目运行截图”。
> screen 方案对应的是 `screen -ls` + 三个日志 tail 的终端窗口。

## 4. 跑测试并截图

测试一定要用**隔离数据库**，不要连服务器上的演示/生产数据库。

```bash
cd ~/DecisionJury

export DATABASE_URL="sqlite:///:memory:"
export ENV=development
export DEEPSEEK_API_KEY=""
export PYTHON_DOTENV_DISABLED=1
export RAG_LIVE_RECORDS=0
export PYTHONIOENCODING=utf-8

# 方式一：如果服务器用 uv
uv run --frozen pytest -p no:cacheprovider tests -q --tb=line --show-capture=no

# 方式二：如果服务器用 deploy/install.sh 创建的 .venv
.venv/bin/python -m pytest -p no:cacheprovider tests -q --tb=line --show-capture=no
```

把终端输出截图，至少包含：

- 命令本身；
- 最后的 `292 passed, 5 failed ...` 汇总行；
- 如需更详细的过程图，可以再跑：

```bash
uv run --frozen pytest -p no:cacheprovider tests -v --tb=short
```

> 注意：`ENV=development` + 真实 `DATABASE_URL` 有重建数据库风险；测试务必同时设置 `DATABASE_URL=sqlite:///:memory:`。
> 不要把 Key 打印到终端或截图里；`DEEPSEEK_API_KEY=""` 是为了测试用 mock，不影响服务端的真实模型配置。

## 8. 截图注意事项

1. 不要截到 `DEEPSEEK_API_KEY`、Token、SSH 密码、服务器密码、数据库密码。
2. 不要截到真实用户隐私数据；演示用模拟数据即可。
3. 截图要能证明“这是当前项目的真实运行结果”，建议保留：
   - 浏览器地址栏（`127.0.0.1:5173` 或 `127.0.0.1:8088`）；
   - 页面标题和关键字段；
   - 终端命令和输出汇总行。
4. 区分真实模型和 mock：
   - 服务器配了 Key 且实际调用 DeepSeek，截图可以写“真实模型调用”；
   - 没配 Key 时页面走本地规则/mock，报告里必须如实说明，不能当成真实 API 验收。
5. 不要修改原始模板文件 `小学期实验报告模板(1).docx`；只改 `docs/report/` 下的内容。
6. 截图放进仓库后，注意不要提交任何临时输出、日志里的密钥或数据库文件。
