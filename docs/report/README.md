# DecisionJury 小学期实验报告 · 协作框架

> 本目录用于把「小学期实验报告」拆成可分工、可合并的 Markdown 章节。
> 最终提交时，把合并后的内容排版进学校提供的 Word 模板
> `小学期实验报告模板(1).docx`，并删除本说明中的占位内容。

## 1. 为什么这样做

- 学校模板要求章节多、图/表/代码展示多，直接多人共写一个 Word 文件容易冲突。
- 项目本身是 5 人分工（A 前端 / B 后端 / C Agent / D RAG / E 工具与工程化），
  报告按模块拆分后，每个人只负责与自己模块相关的章节，Git 冲突少、合并容易。
- 每章节文件都标注了负责人、状态、素材来源和「待填写」占位符，
  队长可以随时通过 `docs/report/README.md` 的进度表检查完成情况。

## 2. 目录结构

```text
docs/report/
  README.md                                  # 本项目说明 + 分工 + 合并流程
  merge_report.py                            # 章节合并脚本
  DecisionJury_小学期实验报告.md              # 运行脚本后的合并版（可提交/排版）
  sections/
    00_封面_摘要_引言.md                      # 封面信息、摘要、关键词、0 引言
    01_项目概述.md                            # 背景、简介、项目计划
    02_需求分析.md                            # 功能需求、非功能需求
    03_设计方案.md                            # 数据描述、功能设计、关键算法、原型图
    04_项目实现.md                            # 总体实现、关键技术实现
    05_项目测试.md                            # 测试环境、缺陷修复、项目展示
    06_项目总结.md                            # 总结体会、不足与改进
    07_参考文献与附录.md                      # 参考文献、附录（可选）
```

## 3. 推荐分工

### 3.1 各章节内部建议细分（避免多人写同一个文件）

- `03_设计方案.md` 建议按小节拆开写：
  - 3.1 数据描述：B / D
  - 3.2 功能设计：A / B（页面功能 + 接口）
  - 3.3 关键算法说明：C（Agent 编排）、D（BM25 检索）、E（成本/评分规则）
  - 3.4 原型图设计：A
- `04_项目实现.md` 建议按模块写：
  - 4.1 总体实现：B / C（架构 + 接口总览）
  - 4.2 关键技术实现：A（前端交互）、B（状态管理与 API）、C（LLM + Agent）、D（RAG）、E（MCP 工具）
- `05_项目测试.md` 建议按模块写：
  - 5.1 测试环境：E
  - 5.2 缺陷与修复：B / C / D / E / A（各自模块）
  - 5.3 项目展示：A（页面截图）、C（Agent 输出）、D（RAG 结果）、E（工具日志）

## 4. 章节文件约定

每个 `sections/*.md` 文件开头都使用统一元信息块：

```markdown
> 负责人：xxx
> 状态：待填写 / 草稿 / 已完成
> 目标页数：约 X 页（Word 排版后）
> 素材：仓库内已有文件路径
```

正文中统一使用以下占位符，方便最后搜索清理：

- `【待填写：...】`：还没有内容，需成员补充。
- `【截图：...】`：需要插入图片/截图，Word 排版时替换。
- `【表格：...】`：需要补充表格数据。
- `【代码：...】`：需要插入关键代码片段。
- `<!-- TODO: ... -->`：HTML 注释，合并后不会显示，仅给成员提醒。

## 5. 单人开发 / 合并流程

### 5.1 拉取最新代码

```bash
git checkout dev
git pull origin dev
git checkout -b feature/report-<你的章节>
```

### 5.2 只写自己负责的章节文件

例如 A 写需求分析和原型图：

```bash
# 在 feature/report-<你的章节> 分支下编辑
docs/report/sections/02_需求分析.md
docs/report/sections/03_设计方案.md   # 仅 3.4 小节
```

### 5.3 本地合并预览

```bash
python docs/report/merge_report.py
```

脚本会按章节顺序生成：

```text
docs/report/DecisionJury_小学期实验报告.md
```

并统计仍未清理的占位符数量。

### 5.4 提交 PR

- 分支命名：`feature/report-<章节名>`。
- PR 标题：`docs: write report section <章节名>`。
- PR 描述：说明改动的章节、覆盖模块、截图/数据来源、未完成事项。
- 合并前由组长检查：所有 `【待填写】` 是否已清理、是否与真实代码/测试结果一致。

### 5.5 合并到 Word 模板

1. 打开 `小学期实验报告模板(1).docx`（或由组长统一分发的同版模板）。
2. 将 `DecisionJury_小学期实验报告.md` 的内容按章节复制到 Word。
3. 按模板要求设置字体：
   - 正文：五号宋体，1.5 倍或单倍行距（以模板为准），首行缩进 2 字符。
   - 标题：五号或相应字号宋体加粗，数字与汉字之间空两格。
   - 英文与数字：Times New Roman。
   - 图表：先插入正文，再添加表题/图题，并在正文中引用（“如表1所示”“如图1所示”）。
   - 公式：使用 MathType 6.0 以上录入，编号用（1）（2）……
4. 删除模板中“参考目录（提交时请删除该内容）”及所有说明性文字。
5. 组长统一 Word 样式、图表编号和参考文献格式后，再定稿。

## 7. 写作注意事项（遵守 AGENTS.md）

- 不编造：功能、测试数据、RAG 命中、工具结果必须与当前代码/实际运行结果一致。
- 截图要求：使用真实运行截图；截图需清晰，展示关键页面或调用过程。
- 引用规范：正文引用图/表/参考文献要在文中写出编号。
- 范围一致：报告只描述 `docs/01_MVP.md` 范围内的购物/时间低风险决策，
  不写医疗、法律、投资等高危场景（可作为“边界/拒绝处理”描述）。
- 完成标准：每个章节提交前自行通读，确认无占位符、无错别字、格式符合模板。
